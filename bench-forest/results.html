Tree persistence is paid once at bulk-write time instead of on every open

On next the account SMT forest (one Merkle tree per vault and per storage map) lives only in memory: every client open reads all map entries back from IndexedDB and rebuilds every tree in wasm, so open time and memory grow linearly with total tracked state. This branch persists the trees in IndexedDB (per-tree metadata, entries, 8-level subtree blobs, a revision counter) and each operation loads only the handful of rows it needs, the same design the sqlite store adopted in rust-sdk PR #2333.

The forest build sits at exactly the same 8,585,216 bytes at every size: the trees stay in IndexedDB and only the rows a read touches ever enter wasm. On next the rebuild allocates memory proportional to total tracked state, reaching ~611 MB for a single 10k-entry map. At 50k entries the next client did not survive setup in this harness: all three attempts died with a wasm panic (unreachable), consistent with the in-memory forest exhausting its address space budget. The 50k open and insert timings for next elsewhere on this page come from the earlier timing run, which completed once.

Counter-increment transactions (execute + prove). Parity in every scenario: execution and proving dominate, and the store's incremental patch writes a handful of rows on both builds, so day-to-day transactions do not pay for the trees living in IndexedDB. Larger sizes could not be exercised against the map account itself because the mock chain treats SDK-created accounts as new, so their first transaction carries the full account state and exceeds the protocol's update-size limit past ~1k entries.

Trade-off: bulk writes of huge maps

Creating the account, i.e. persisting all N map entries at once.

Map entries next forest ratio
1,000 203 ms 1.47 s 7.2x
10,000 3.95 s 46.6 s 11.8x
50,000 43.2 s 372.7 s 8.6x
This is the cost that used to be paid on every open, moved to a one-time write. Persisting a tree means writing its inner nodes: ~6-7 subtree rows per entry for hash-distributed keys (measured 6,244 subtree rows for 1,000 entries), on top of the entry rows both builds write. IndexedDB throughput is per record: a raw probe (70,000 puts of ~600-byte records in one transaction, no SDK code involved) sustains only ~1,500-2,300 records/s in Chromium, which fully accounts for the times above. Serialization strategy, base64 removal, transaction durability and index count were each measured and none moves the needle; row count is the only lever. Adjacent-position packing was prototyped and reverted: hashed keys make deep subtree positions sparse, so 16-way packing collapsed only 5.6% of rows.

In practice this cost is only visible when importing or creating an account whose storage map has tens of thousands of entries; ordinary transactions touch a few rows. It is also specific to IndexedDB rather than to the design. The sqlite store persists the same ~6-7 rows per entry, but inside one transaction SQLite sustains hundreds of thousands of row inserts per second (they are B-tree appends into a single local file), so populating a 50,000-entry map costs about 4 s there. In the browser every put crosses from wasm through the browser process into LevelDB individually, which is where the fixed ~1,500-2,300 records/s ceiling comes from.

Since row count is the only lever, the way to make this better for IndexedDB is to write fewer rows. With hash-distributed keys almost all of those ~6-7 subtree rows hold a single leaf, and a single-leaf subtree is fully determined by its one entry, so the store could skip persisting those rows and reconstruct them from the entry at read time. That would eliminate most of the puts behind the numbers above and shrink both stores' disk footprint, at the price of a little reconstruction work per read. It requires support in the shared forest_backend module in rust-client, so it is left as the main follow-up for whoever continues this work.

Methodology and caveats

  • Harness: bench-forest/run-bench.mjs. Static server over each build's dist/st bundle, fresh Chromium context (empty IndexedDB) per size, same high-level API calls on both builds. Both bundles are release builds.
  • Mock client (MidenClient.createMock) over the real IndexedDB store; no network. Account creation time excludes building the StorageMap object and compiling the contract component.
  • One sample per (variant, size) for insert/open; reads are medians of 30. Run-to-run noise on the big inserts is around 10%.
  • Memory is wasm linear memory after a reload, client open and 31 witness reads. performance.memory.usedJSHeapSize was measured too but only covers the V8 heap, missing wasm entirely. The small-account transaction runs while the map account is tracked in the same store; it is skipped at N=50k, where the mock chain panics on any transaction (memory and small-tx numbers come from a second run, results-*-mem.json).
  • Raw IndexedDB throughput probe: bench-forest/idb-throughput.mjs. Per-table disk attribution helper: bench-forest/disk-breakdown.js.
Branch state at measurement: feature commit 57e4eb2 plus review fixes 9bcb0f4, d55d4c3, c5aea8e and the write-path performance pass 0fc3a1f (serde plain-object transport, raw Uint8Array blobs, single bulkGet expectation check, native base64 decoder on reads, logarithmic cache maintenance).
